# 12: Adversarial review of note 11 (streaming, revision 2)

*2026-10-27. Review of `docs/research/11-streaming-r2.md` against notes 09 and 10, `AGENTS.md`, `docs/plan.md`, `docs/interface.md` (protocol 2), the code at `aa217e0` plus the uncommitted groups work (treated as in flux), pipekit, commonkit and SoundCraft. The maintainer's framing stands: soundness, coherence, fit and whether a framework would do the job, not whether a use exists today. Seven time-boxed experiments were run (section 3); everything is under `claude-debug/streaming-review2/`. Nothing in the repository was changed except this file and its PDF.*

## 1. Verdict

**Accept with changes.** Revision 2 adopts the substance of all 13 required changes from note 10, and its own corrections of that review are right in every case I could check against the code. The load-bearing mechanisms hold up under experiment: a crossbeam data channel plus a credit channel gives lossless backpressure, growth by issuing permits, a wait-for detector that resolves the window diamond with output equal to the sequential reference and fails by name at the cap; the `replace` carry is exact at every cut; `lower` is context-sensitive at character cuts and safe at line cuts in both Rust and Python; 23 of the 25 SoundCraft effects are bit-identical at block sizes 1, 64, 256 and 4096; per-chunk npy framing costs about 22 µs per 21 ms of stereo audio in Python.

What does not hold is narrower than note 10's objections but still has to be fixed before the plan is built:

1. The deadlock conformance case is incoherent with the join rule. §13.3 builds the diamond with `text.window`, which §5.4 and §13.3 mark `clock: new`, and §7.2 refuses a `time` join whose inputs are not on one clock. The only join legal behind that window is `latest`, which has no lockstep wait and so can't deadlock.
2. Live parameters are injected "to the tail of the target node's input queue" from off the run path, into an edge whose capacity is governed by credit. Either the host takes a permit, and `stream.set` blocks on a full queue, or it doesn't, and the data channel's `cap_max` bound is broken. Revision 2 says neither.
3. The inline-tap numbers contradict their own limits: a 50 ms stereo batch is about 19 KiB raw and 25 KiB in base64, over `max_tap_inline` (16 KiB); four audio taps are about 2 MiB/s, over `max_tap_rate` (1 MiB/s). The measurement Q1 is told to make can't pass as specified.
4. "The response streams credit back" on a chunked `POST` is full-duplex HTTP, which neither `ureq` 3 (the host's client) nor `tiny_http` (the engine's server) does. D5's closure ("WebSocket no longer needed for push") rests on it.
5. dora-rs's `queue_policy: backpressure` is not credit. In a run on this Mac (dora 1.1.0) the producer was never throttled and the daemon dropped the oldest at a hard cap of 100, logging "dropping oldest to prevent OOM". §14's "either dora-rs's `backpressure` or explicit credit" offers two things as equivalent that are not.
6. The panic path (§9.4) says "exactly today's rebuild", but today's rebuild is the worker loop's own `catch_unwind` around `exec::run` (`crates/engine/src/host.rs:461-516`). A stream run on its own coordinator thread (§9.3) has to signal the worker, and the batch run that may be in flight on the same `Arc<Engine>` is not mentioned.

None of these changes the model. Section 7 lists the required changes.

## 4. Findings

### 4.1 Soundness

**F1. The deadlock case contradicts the join rule.** §7.2: a `time` join's inputs "MUST be on one clock (a graph error otherwise)". §5.4: `clock: new` marks "windows with a hop". §13.3: `text.window` is "N lines, hop H (`clock: new`, rate-changing), to build the diamond for the deadlock case". A `time` join of `lines` and `window(lines)` is therefore refused, so the Q1 criterion "the window diamond resolves by growth with output equal to batch" can't be built with a `time` join. With a `latest` join there is no lockstep wait: the join reads its primary and samples the secondary, and §8.3's "a join waits on the input with the minimum frontier" doesn't describe it. Experiment 3 built the diamond the only way the rules allow: a sliding window with hop 1, `clock: same`, `latency: N−1`. Revision 2 must give `text.window` that form for the deadlock corpus, or define how a `latest` join enters the wait-for graph.

**F2. Live parameters and credit.** §6 says the host "appends a `param` item to the tail of the target node's input queue, stamped `at` = that queue's tail offset", and §10.2 says `stream.set` is "off the run path". §8.2 says the data channel never blocks because `cap` never exceeds `cap_max` and every `send` is preceded by a permit. A second writer breaks that: if the host takes a permit, `stream.set` blocks behind a full queue, which is on the run path; if it doesn't, the data channel can be full and `send` blocks or fails. The channel doesn't expose a tail offset either. The clean form is the one §8.2 already has for cancel: a per-node control channel in the `select!`, with the node ordering the `param` against its data by the stamped `at` (apply at the first item whose offset is ≥ `at`). One writer per data edge, one `applied_at` semantics; the same at a fused island's input.

**F3. Inline taps contradict their limits.** §11: a 20 ms stereo `f32` block is 7.5 KiB and "50 ms batches are about 19 KiB, so about 0.5 MB/s per tap". §10.6: `max_tap_inline` is 16 KiB on the socket and `max_tap_rate` 1 MiB/s per session, measured "under 4 audio taps" (§11, D29). Base64 inflates 19 KiB to 25 KiB, over the per-append cap, and four taps at 0.5 MB/s are 2 MB/s, double the session cap. The per-append cap also conflicts with spec 10.6's "batches `append` to ≥ 50 ms or ≥ 64 KiB". Either the batch is 25 ms stereo (or 50 ms mono), or the cap is 32 KiB, and the rate cap must be at least the number of taps the measurement uses.

**F4. HTTP push is not duplex.** §10.2 mode 3: "a binary `POST /v1/streams/{run}/in/{node}.{port}` with a chunked body of npy frames. The response streams credit back." That needs the client to read the response while still writing the body. `ureq` 3.5 (`Cargo.toml:33`) runs a sequential state machine, `SendRequest → Await100 → RecvResponse → RecvBody` (`ureq-3.5.0/src/run.rs:178-221`): the body is complete before the response is read. `tiny_http` 0.12's `respond` takes `self` (`src/request.rs:432`), so the server can't answer while still reading; only `upgrade` (`:305`) hands back a raw stream, which is a WebSocket-shaped path. Credit must therefore come back on a second request (a long-poll `GET`, which spec 16.4 already has) or D5 (WebSocket) is needed after all; §16's "D5 … no longer needed for push" doesn't hold with the chosen stack. Credit over a second connection is sound if granted in batches, which `{credit: n}` already allows.

**F5. Panic with a stream slot.** §9.4 ends "Then exactly today's rebuild (`host.rs:485-516`)". That code is inside `worker_loop`, triggered by its own `catch_unwind` around `exec::run`. A stream coordinator thread (§9.3) that catches a panic must signal the worker, which must then discard the engine while a *batch* run may be executing on the same `Arc<Engine>`, whose reply and memo insert then land after the engine was declared untrusted. The spec needs one sentence: a stream panic cancels the batch run in flight (failed as `engine`), then rebuilds. Also, the memo is a worker local (`host.rs:467`), so §9.3's "lookups go the same way" makes a stream's start wait behind whatever batch node is running; a `Mutex<Memo>` in `Shared` is simpler and off the run path.

**F6. `flush` is one call; the cooperative rule needs it resumable.** §9.1: a cooperative node is runnable "when it has input and room for its declared `max_out`, so a burst can't overfill a queue by more than one call's output". §13.1: `fn flush(&mut self, out: &mut Out, cx: &mut Cx)`. A reverb's flush is up to 60 s of tail (`fx.rs:23`), about 2,800 blocks, which is far more than any `max_out`. Inside a pull-driven island this is fine (the tail is pulled block by block), but at an island boundary or in the cooperative executor for a non-`Send` core, a single-shot `flush` into a bounded queue either blocks the only thread or overfills. `flush` should return whether it has more (`Pending`/`Done`), or be modelled as `process(Eos)` called repeatedly while it emits.

**F7. `Delivery` can't be reused as is.** §8.1 says the proto `Delivery` enum "describes event queues, data edges and taps alike", but its variants are `Ordered`, `Latest(String)` with a key, and `DropOldest(usize)` with a count (`crates/proto/src/event.rs:274-281`). A data edge has `size` and `policy` as separate fields and no key; `conflate` has no key. One enum needs new variants or the edge policy is its own type. Small, but Q0 writes this into the schema.

**F8. The `latest` secondary's default policy.** With `block` as the default between nodes (D27), a `latest` join's secondary input blocks its producer once 8 items are queued, and the join drains it only when a primary item arrives. In a diamond this stalls the shared source (the cycle in F1). The natural default for a `latest` secondary is `conflate`, and the editor should say so.

**F9. Growth time and the 1 s criterion.** Experiment 3 needed ten growth steps (two edges, 4 → 128 each) for a window of 200 with T = 100 ms, 1.45 s. A diamond with latency N resolves in about log2(N/cap) × (edges in the cycle) × (T + tick); with revision 2's T = 200 ms and a 250 ms tick it is slower. The criterion "fails within 1 s naming the join" at a small cap held here only just (1.26 s). Either grow geometrically across all full edges in the cycle at once, or state the bound as a function of N.

**F10. Byte budget (A12).** The 64 MiB budget bounds queues, and nothing else. State the four separate caps (queues, accumulate per type, retention, join buffers) and that accumulate of a 40-minute stereo stream is allowed up to `MAX_SAMPLES`.

**F11. Self-healing status (A11).** D36 heals state. Preview payloads are not in the header; say that a lost `preview` is repaired by `run.watch` or `run.get`, and that the stats `status` field is dedup'd by `(publisher, publisher_seq)`, so a header that repeats the last record is a no-op, which is what makes it safe to send every interval.

**F12. Smaller points.** (a) `run.multi` (spec 5.3) means "several runs may execute concurrently"; §9.3 redefines it as one stream beside the worker while `max_runs` stays 1. Advertise `max_streams` and leave `run.multi` alone. (b) Python strings may hold lone surrogates (`surrogateescape`), which are not scalar values and which Rust refuses; the TEXT corpus should pin the behaviour. (c) `render_with_tail` maps non-finite output to 0.0 (`fx.rs:188`) and passes a 1024-long scratch zeroed past `n`; the island must do both. (d) A line rechunker on a stream with no newline buffers without bound; it needs a cap that becomes a node error. (e) `de_esser` fails only at block 1 and `dither` is per call; the multi-size test should let a plugin declare "sizes ≥ 64" and keep `dither` out of the equality set rather than `fixed_block` forever.

### 4.2 Fit with the existing system

- **The run model, taps outside the ring, capability gating, `stream.inputs`, commands in `stream_cmds.rs`:** all fit spec 8, 9.7, 5.3 and golden rule 4 as note 10 asked. §10.6's row-by-row list of spec changes is the right form for Q0.
- **The session (`crates/session/src/run.rs`):** `apply_event` ignores everything but `Status` and `RunReply` (`run.rs:292-311`), staleness clears in `apply_reply` (`run.rs:366-373`), and `progress()` counts finished nodes (`run.rs:467-470`): verified; §12's changes are the right ones. These files are in flux under the groups work, so Q2 should expect to rebase.
- **`plumcraft-graph`:** `output_is_list` and `is_mapped` exist at HEAD (`lib.rs:549-572`); `output_is_stream` beside them is the natural extension. The committed `check_wire` (`ports.rs:122`) has no notion of units or clocks, so the "refused before running" criterion in Q2 is new code, not a flag.
- **The host (`crates/engine/src/host.rs`):** one worker, memo as a local, panic rebuild in the loop. F5 is the fit problem.
- **Spec 16.4 as built:** "`POST /v1/rpc` carries every operation, `events.poll` included; SSE comes later". F4 follows from this.
- **pipekit:** `CONCURRENCY = 1` is the default (`node.py:389`), so "pin it" is the right wording. The credit queue and barrier work are new pipekit features, as revision 2 says.
- **commonkit:** unchanged, correctly. The 340 MB per live tap argument against commonkit for taps is right.
- **SoundCraft:** `Plugin` (`dsp/src/lib.rs:195-212`) maps onto `StreamState` as claimed; `MixEngine::render` (`mix/src/lib.rs:641`) is the precedent; `CaptureRing` (`playback/src/record.rs:46`) is atomics without `unsafe`, so the push source design is consistent with AGENTS.md rule 2.

### 4.3 Frameworks

- **crossbeam:** adopt, as note 10 said and experiment 3 confirms. The one correction (no resize) is right, and the credit composition is the standard way around it.
- **dora-rs:** the vocabulary is as note 10 described, and it runs here. But experiment 7 shows `backpressure` is a soft policy with a hard-cap drop in 1.1.0, and its binary says the direct Zenoh path "cannot honor that policy". For a *lossless* long-file stream across machines, dora as of 1.1.0 is not a substitute for credit, so Q6's comparison should test exactly this and not assume it. For live, lossy streams it is fine.
- **Arrow IPC:** experiment 4 shows it is cheaper per batch than npy in steady state (4.0 vs 6.9 µs encode, 0.7 vs 15.1 µs decode) and 64 B larger per chunk; both are negligible. D38(a) stands on cost; the reason to prefer Arrow would be `TABLE` streams, which revision 2 already reserves it for.
- **GStreamer:** not installed or tested, by the download rule; revision 2 borrows its in-band events correctly and doesn't depend on it.
- **timely frontiers, Flink barriers, GNU Radio tags:** borrowed as ideas; the uses in §7 and §14 are faithful.

## 6. Estimate

Q1's exit list has 21 bullet criteria covering the SDK, two channel kinds, in-band items, frontiers, two joins, the detector with growth, the stream slot, stats with headers, inline taps with retention, the inactivity timeout, idle cancel, `detach`, panic handling, eleven text nodes and a CLI. At the plan's own rate (S5: 6–8 days for one binding and its supervisor) 11–14 days is optimistic by about half. Q4's five-minute bit-exact chain is supported by experiment 1, but "mic → gain → compressor under 150 ms for 10 minutes with zero drops" on cpal is new UI and engine code (jitter buffer, streaming resampler) in the same 11–14 days.

## 7. Required changes

1. **Fix the deadlock corpus (F1).** Give `text.window` a `clock: same` form (hop 1, `latency: N−1`) for the diamond, or specify how a `latest` join enters the wait-for graph. State the resolution-time bound as a function of N (F9), or grow every full edge in the cycle together.
2. **Specify live-parameter injection (F2).** One writer per data edge. Deliver `param` on the node's control channel and order it by `at` at the consumer; define `at` as the producer's last sent offset read from a per-edge atomic. Keep `stream.set` off the run path by construction.
